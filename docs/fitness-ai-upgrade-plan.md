# 健身 AI 平台改造实施方案

> 项目：`knowledge-agent`
>
> 方案版本：V1.0
>
> 编制日期：2026-10-16
>
> 当前状态：阶段 0 已完成，阶段 1 第一轮实现中

---

## 1. 项目改造目标

将当前的“企业知识库 + AI 问答系统”逐步改造成面向大众年轻用户的健身 AI 综合平台。

最终目标包括：

1. AI 健身教练
2. 健身知识库
3. 个性化训练计划
4. 训练打卡与数据统计
5. 饮食和营养管理
6. 拍照识餐
7. 健身知识图谱
8. 管理后台

改造原则：

- 保留当前 Docker、FastAPI、PostgreSQL、MongoDB、Elasticsearch、Milvus、Neo4j、RabbitMQ、Redis、RustFS 等基础设施。
- 不一次性重写项目，按阶段完成可验证的小闭环。
- 每次只修改一个主要功能，修改后立即测试。
- 先实现 MVP，再增加复杂能力。
- 先复用已有接口，确有必要时再新增接口。
- 不因为 GitNexus FTS 搜索不可用而阻塞业务开发；它只影响代码分析辅助功能，不影响项目运行。

# 6. 阶段 2：AI 教练健身化

## 目标

把当前企业知识库助手改造成健身 AI 教练。

## 现有调用链

```text
前端问题
    ↓
api/ai.py
    ↓
检索服务
    ├── Elasticsearch
    ├── Milvus
    └── 联网搜索
    ↓
services/llm_service.py
    ↓
大模型
    ↓
前端展示答案
```

## 实施任务

### 6.1 修改系统提示词

主要文件：

```text
services/llm_service.py
```

AI 需要具备以下角色约束：

- 面向普通大众提供健身建议。
- 根据用户目标、经验和身体情况回答。
- 优先使用健身知识库内容。
- 涉及疼痛、伤病和极端减重时必须风险提示。
- 不替代医生、营养师和专业教练。
- 不鼓励危险动作、极端节食和过度训练。

### 6.2 增加健身档案上下文

AI 后续需要读取：

```text
身高
体重
年龄
性别
训练目标
训练经验
每周训练次数
可用器械
身体限制
```

### 6.3 统一 AI 返回结构

建议逐步支持：

```json
{
  "answer": "核心回答",
  "summary": "一句话结论",
  "actions": ["建议一", "建议二"],
  "warnings": ["注意事项"],
  "sources": ["参考文档"]
}
```

## 验收标准

输入：

```text
我想减脂，每周训练三次，应该怎么安排？
```

AI 应该能够返回：

- 目标分析
- 每周训练建议
- 饮食方向
- 执行步骤
- 风险提醒
- 参考知识来源

# 8. 阶段 4：训练计划与智能意图路由

## 目标

让 AI 不只是回答问题，还能够生成并保存训练计划。

## 第一版意图分类

```text
knowledge   健身知识问答
training    训练计划
nutrition   饮食营养
progress    训练进度
safety      风险和禁忌
```

示例：

```text
“深蹲锻炼哪里？”
→ knowledge

“帮我制定一套增肌计划”
→ training

“晚餐吃鸡胸肉可以吗？”
→ nutrition

“我膝盖疼还能深蹲吗？”
→ safety
```

## 训练计划生成流程

```text
读取健身档案
    ↓
识别训练目标
    ↓
判断训练经验
    ↓
判断器械条件
    ↓
检索健身知识库
    ↓
生成训练计划
    ↓
保存 TrainingPlan
    ↓
前端展示
```

## 实施原则

第一版不立即引入复杂多 Agent 框架，先实现一个清晰的意图路由器。等单体流程稳定后，再考虑 LangGraph 或多 Agent 编排。

## 验收标准

- 能根据目标生成训练计划。
- 计划可以保存、查看和修改。
- 计划包含训练日、动作、组数、次数和休息时间。
- 训练计划会考虑用户经验、器械和身体限制。
- 危险或不合理条件会给出提醒。

## 目标

## 知识分类

```text

训练计划
营养知识
减脂知识
增肌知识
运动康复
拉伸恢复
伤病禁忌
运动心理
```

## 建议知识字段

```text
category
 difficulty
target_muscle
equipment
goal
risk_level
source
```

## 知识图谱关系

```text
训练目标 → 推荐 → 训练计划
训练计划 → 包含 → 训练动作
训练动作 → 锻炼 → 目标肌群
训练动作 → 需要 → 器械
身体问题 → 不适合 → 训练动作
食物 → 含有 → 营养素
营养素 → 支持 → 健身目标
```

## 现有接口

```text

GET  /neo4j/entity_relationship?doc_id=文档ID
GET  /neo4j/overview
```

当前发布流程中的知识图谱自动生成逻辑需要单独确认，不要在没有测试的情况下直接恢复自动流程。

## 验收标准

- 可以上传健身知识文档。
- 可以发布和删除文档。
- 可以为文档生成实体关系。
- Neo4j 中可以查询节点和关系。

# 14. 每次开发必须遵守的流程

每个功能都按下面的闭环进行：

```text
1. 明确本次只做一个功能
2. 查看相关现有代码
3. 使用 GitNexus 做影响分析（如果工具可用）
4. 列出需要修改的文件
5. 先修改后端接口或数据模型
6. 启动并测试后端
7. 接入前端页面
8. 测试正常流程和异常流程
9. 查看 git diff
10. 执行 GitNexus detect-changes
11. 更新本方案文档状态
```

特别注意：

- 修改函数、类或方法前，先进行影响分析。
- 遇到 `HIGH`、`CRITICAL` 或 `UNKNOWN` 风险，不得直接忽略。
- 不使用 `git reset --hard`。
- 不使用 `git checkout --` 覆盖已有修改。
- 不一次修改多个无关模块。
- 每完成一个阶段，都必须可以演示和回滚。
