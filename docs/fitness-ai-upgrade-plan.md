## 1. 项目改造目标

将当前的“企业知识库 + AI 问答系统”逐步改造成面向大众年轻用户的健身 AI 综合平台。

最终目标包括：

1. AI 健身教练
2. 健身知识库
3. 个性化训练计划
4. 训练打卡与数据统计
5. 饮食和营养管理
6. 拍照识餐
7. 健身知识图谱
8. 管理后台

改造原则：

- 保留当前 Docker、FastAPI、PostgreSQL、MongoDB、Elasticsearch、Milvus、Neo4j、RabbitMQ、Redis、RustFS 等基础设施。
- 不一次性重写项目，按阶段完成可验证的小闭环。
- 每次只修改一个主要功能，修改后立即测试。
- 先实现 MVP，再增加复杂能力。
- 先复用已有接口，确有必要时再新增接口。
- 不因为 GitNexus FTS 搜索不可用而阻塞业务开发；它只影响代码分析辅助功能，不影响项目运行。

# 6. 阶段 2：AI 教练健身化

## 目标

把当前企业知识库助手改造成健身 AI 教练。

## 当前实施记录（2026-10-26）

阶段 1 已由用户完成浏览器验收。阶段 2 第一项（健身教练提示词与安全边界）已完成：

- 明确 AI 提供一般健身建议，不做疾病诊断或治疗。
- 补充疼痛、伤病、急症信号、特殊健康情况及极端饮食的安全处理规则。
- 明确知识库/网页内容和跨会话记忆均为待评估数据，不是可执行指令。
- 规范真实来源引用；无检索资料时可给谨慎的一般建议，但必须说明知识库未命中，不得编造引用。
- 保留现有普通问答、SSE 流式响应和 `sources` 引用结构。
- 新增单元测试，覆盖安全边界和消息组装兼容性。

阶段 2 个性化档案上下文已接入普通问答、SSE 流式问答和训练计划草稿生成。原有档案字段为身高、体重、目标和经验；本轮补充年龄、性别、每周训练天数、可用器械和身体限制，增量迁移为 `migrations/20261026_02_extend_kh_fitness_profile.sql`。该迁移尚未替用户执行，执行方法见 `docs/fitness-coach-phase2-acceptance.md`。

- 普通问答与流式问答只按当前登录账号从 PostgreSQL 读取档案，不接受客户端请求体覆盖档案。
- 未填写的字段保持未知；性别“不愿透露”不会注入提示词，身体限制按用户自述背景处理。
- 训练计划草稿优先采用本次请求明确填写的器械、训练天数和限制，其次使用账号档案；知识库动作只有在检索片段确实支持动作名称时才保留“知识库支持”及来源编号。
- 训练计划页面会把当前账号档案中的器械、每周训练天数和身体限制实际填入输入框，不只是显示占位提示；用户手动修改后不被重新加载覆盖，切换账号时清除上一账号表单值。
- 普通问答仍返回现有 `{content, sources}`，流式接口仍使用现有 SSE 事件，避免破坏前端消费契约。统一 JSON 字段（summary/actions/warnings）不是本阶段已交付接口。
- 自动化测试覆盖普通问答、流式问答和训练计划生成的档案传递、安全提示词、未知字段以及来源编号过滤；本轮定向后端测试 46 项通过，前端语法检查通过。

阶段 2 的代码实现完成，待用户执行新增迁移并按验收清单确认档案保存、账号隔离和 AI 回答个性化。

当前普通问答和流式问答的 LLM 调用都在 `api/ai.py` 中完成；`services/llm_service.py` 不是这两条问答链路的调用入口，它主要提供图谱实体关系抽取能力。

## 阶段 3.1：账号健身档案持久化（已完成验收）

本小步只覆盖已有的四个档案字段：身高、体重、训练目标、训练经验；不代表阶段 3 全部完成。

- `kh_fitness_profile` 以 `user_id` 为主键和外键，每个账号最多一份档案。
- `GET/PUT /fitness/profile` 从 JWT 当前用户身份读写，客户端不能指定 `user_id`。
- AI 普通问答和流式问答统一从 PostgreSQL 读取档案；旧客户端即使仍发送档案请求体，也不会覆盖数据库数据。
- 前端档案页面读写后端接口；旧的账号级 `localStorage` 档案在首次同步时尝试迁移，成功后删除本机副本。
- 旧全局键 `ironflow_profile` 不自动归属到当前账号；仅在数据库读取成功且账号尚无档案时，将旧值填入表单供用户核对，用户显式保存后才写入当前账号。
- SQL 迁移文件：`migrations/20261021_01_create_kh_fitness_profile.sql`。用户已在当前验收数据库执行迁移，并确认接口、档案持久化和 AI 问答验收通过；其他环境仍需单独执行迁移。

# 8. 阶段 4：训练计划与智能意图路由

## 阶段 4.1：训练计划数据模型和账号读写接口（已验收）

- PostgreSQL 表 `kh_training_plan` 保存计划名称、目标、经验和按天组织的动作明细（JSONB）。
- `GET/POST /training/plans` 支持当前账号分页查看和新建计划。
- `GET/PUT /training/plans/{plan_id}` 支持查看及完整修改当前账号的计划。
- 所有读写以 JWT 当前用户 ID 限定归属；请求体不接受 `user_id`，其他账号的计划统一返回 404。
- SQL 迁移：`migrations/20261022_01_create_kh_training_plan.sql`。代码不会在启动时自动修改数据库；用户已执行迁移并验收创建、列表、详情、修改和读回持久化。
- 计划数据校验训练日、休息日、动作名称、组数、次数和休息时间等字段。

本步只实现训练计划的存储和读写闭环，不包含 AI 意图识别、自动生成训练计划、前端计划管理页面及训练打卡。

### 阶段 4.1 验收标准

- 执行迁移后，用户可以创建、查询、分页查看和修改训练计划。
- 请求中的 `user_id` 被拒绝；用户无法通过计划 ID 读取或修改其他账号的数据。
- 非法日期安排或动作字段在写入前被 API 校验拒绝。
- 重新读取计划时，训练日、动作、组数、次数、休息时间和备注保持一致。

## 阶段 4.2：AI 生成训练计划（已完成验收）

- `POST /training/plans/generate` 读取当前账号档案、合并用户显式填写的器械/训练天数/身体限制，并检索本次知识库资料，返回结构化草稿。
- 生成动作带有 `evidence_type` 和 `source_refs`；服务端只保留指向本次检索到知识库来源的编号，其余统一标为“一般建议”。
- 生成接口不写数据库。用户在前端检查安排和来源后点击“确认并保存”，才调用已验收的 `POST /training/plans`。
- 前端增加训练计划入口、生成表单、草稿预览、知识来源和已保存计划列表；现阶段不提供计划删除和编辑界面。

### 阶段 4.2 验收标准

- 用户档案目标和训练经验能影响计划，模型不能覆盖档案中已填写的目标/经验。
- 未填写的器械、训练频率和身体条件不会被当作已知事实；缺少信息要在草稿说明。
- 仅有有效知识库来源编号的动作可标为“知识库支持”；未命中资料或引用无效时标为“一般建议”。
- 生成草稿不会持久化；只有点击确认保存后，计划才出现在已保存列表并能重新读取。

## 阶段 4.3：AI 教练训练计划意图路由（第一版，已验收）

- 将原始请求带入训练计划页的需求输入框，不自动调用生成接口，也不自动保存。

- 当前使用前端轻量关键词规则，仅处理训练计划意图；其他营养、进度等业务路由不在本小步范围内。

### 阶段 4.3 验收标准

## 当前实现

- `kh_training_record` 保存账号、计划/训练日快照、训练状态、实际动作数据、服务端计算的训练时长和可选体重。
- `POST /training/workouts` 开始训练；`POST /training/workouts/{id}/complete` 完成训练。时长由服务端按开始/完成时间计算，不接受客户端伪造。
- `GET /training/workouts`、详情、取消和删除接口按 JWT 当前账号隔离；进行中和已取消记录不计入统计。
- `GET /training/stats` 返回本周训练次数、连续打卡天数、本周时长、训练容量、主要训练重点和体重变化。
- 训练计划页支持从已保存计划开始训练、填写实际组数/次数/重量、完成/继续/取消训练和查看/删除记录；首页读取真实统计并提供加载、空数据和错误状态。
- 迁移文件：`migrations/20261022_02_create_kh_training_record.sql`。代码不会在启动时自动修改数据库，需在目标 PostgreSQL 数据库中手动执行迁移。

## 验收标准

- 用户可以开始和完成一次训练。
- 训练记录可以查看、删除。
- 首页展示真实统计数据。
- 完成记录不会修改可复用的训练计划模板；训练实例状态由训练记录自身维护。
- 不同用户之间的数据隔离正常。

## 验收操作

1. 将迁移文件复制到 PostgreSQL 容器：`docker compose cp .\migrations\20261022_02_create_kh_training_record.sql postgres:/tmp/training-record.sql`。
2. 在 PowerShell 读取容器实际配置并执行迁移：
   ```powershell
   $pgUser = (docker compose exec -T postgres printenv POSTGRES_USER).Trim()
   $pgDb = (docker compose exec -T postgres printenv POSTGRES_DB).Trim()
   docker compose exec -T postgres psql -U $pgUser -d $pgDb -f /tmp/training-record.sql
   ```
3. 登录前端，打开“训练计划”，打开已保存计划，点击某个训练日的“开始这天训练”。
4. 填写实际组数、次数和可选重量，点击“完成训练”；确认记录显示“已完成”，首页训练次数、时长和训练容量随之更新。
5. 开始一次训练后刷新页面，确认记录仍为“进行中”，可以继续或取消；取消记录不计入统计。
6. 删除一条已完成记录，确认历史消失且统计重新计算；用另一账号确认无法读取该记录。
