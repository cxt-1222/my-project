## Context

当前 `frontend/app.js` 使用页面级 `state.isStreaming` 和单个 `#typingMessage`，因此一个会话开始生成后，整个聊天页面都被视为忙碌。会话切换逻辑只切换 `activeSessionId` 和已保存消息，未保存每个会话的活动流状态。后端 `api/ai.py` 的流式接口使用异步模型调用，当前没有应用级全局队列，但同一会话的历史读取、用户消息写入和回答写入可能在并发请求中交错。

本设计先以同一浏览器页面的多会话并行体验为目标，保持现有 SSE API、鉴权、知识库检索和会话数据模型兼容。

## Goals / Non-Goals

**Goals:**

- 将流状态从页面级改为 `session_id` 级，支持不同会话同时生成。
- 为每个会话保存活动请求、增量答案、来源、错误和完成状态，并在会话切换时恢复正确视图。
- 保证同一会话最多一个活动请求，避免上下文顺序不确定。
- 处理流的完成、失败、超时、取消、退出登录和删除会话，避免迟到事件污染其他会话。
- 用可测试的状态模型覆盖不同完成顺序、切换、失败隔离和来源归属。

**Non-Goals:**

- 不实现跨设备实时同步、WebSocket、多用户广播或无限并发。
- 不默认引入后端任务队列、消息中间件或持久化“等待队列”。
- 不允许同一会话并行生成多个回答。
- 不改变模型提示词、知识库检索排序、SSE 事件名称或训练计划功能。

## Decisions

### 1. 使用按会话索引的前端运行时状态

新增类似 `activeStreams[sessionId]` 的状态表，每项包含请求控制器、状态 (`streaming/succeeded/failed/cancelled`)、已接收文本、来源、错误和是否已提交用户消息。`state.activeSessionId` 只负责当前显示会话，不再决定所有流是否可发送。

选择按会话状态而不是单个布尔锁，是因为会话切换是现有页面的核心操作；它能支持不同会话独立并发，同时保留同一会话的顺序保护。

### 2. 每个会话使用独立的临时消息节点或统一重绘

不再依赖全局唯一 `#typingMessage`。流事件到达时只更新对应会话的运行时消息；如果该会话当前可见，只更新对应流式回答的稳定文本节点和必要状态，不重建聊天消息列表；来源事件单独更新来源区域。首次显示流式回答、切换会话和回答完成时才完整渲染。后台会话只更新内存状态。切换回会话时，按“已保存消息 + 活动流临时消息”渲染，避免 A 的增量文本出现在 B 中。

临时流消息不提前写入最终历史数组，只有收到 `done` 后才转换为 assistant 消息并持久化。失败或取消时保留用户消息是否已经提交的既有语义，并显示该会话自己的错误状态。

Composer 中尚未发送的文本也按当前 `session_id` 保存。切换或新建会话时先保存旧会话草稿，再恢复目标会话草稿；新会话默认空白。没有活动会话时输入的初始草稿会在首次创建会话时迁移过去。

### 3. 同一会话使用前端检查和后端会话级 try-lock，其他会话不受影响

发送前先检查 `activeStreams[sessionId]`；若存在未完成流，仅提示“当前对话正在回答”，不发送、不排队。检查和登记必须在创建异步任务前完成，避免连续点击产生两个请求。发送按钮只根据当前会话状态启用/禁用，不能再由全局 `state.isStreaming` 控制。

仅有前端检查无法阻止另一个标签页或 API 客户端并发提交同一会话，而后端当前会先读取历史、再保存用户问题、最后在模型完成后保存回答，这可能形成错误的消息顺序。因此后端增加按 `(user_id, session_id)` 索引的短作用域 try-lock：同会话已有流时立即返回明确冲突，不等待；不同 session_id 不共享锁，仍可并行。当前 Docker 启动配置为单 Uvicorn worker，首版可使用进程内 keyed lock；如启用多 worker/多副本，必须改为分布式锁后才能宣称跨进程保护。

### 4. 使用 AbortController 管理生命周期

每个活动流绑定独立 `AbortController`。退出登录时取消所有活动流并递增账号/页面代次；当前页面禁止删除正在生成的会话，直到回答结束。所有事件处理器在写入状态前核对 session id、账号代次和活动请求实例，迟到事件直接丢弃。

### 5. 后端保持接口兼容，增加同会话一致性保护

不改变 `/ai/invoke_stream` 的请求和 SSE 响应格式。后端在流开始前按 `(user_id, session_id)` 尝试获取会话锁；已锁定则返回 HTTP 409/明确业务错误，不排队。锁在 SSE 正常结束、失败、客户端断开或取消时必须经 `finally` 释放。无 `session_id` 的请求不因其他会话而阻塞。首版进程内锁依赖当前单 worker 部署；多 worker/多副本发布前必须换成 Redis 等分布式锁，不能将进程内锁误认为全局锁。

### 6. 测试采用可控 SSE 流和不同完成顺序

前端测试使用可控的 mock `fetch`/ReadableStream，让会话 A、B 的 delta、sources、done、error 以任意顺序到达。重点验证状态归属和 UI 切换，而不是依赖真实模型响应时间。后端只做兼容性和同会话并发回归，不把模型供应商限流误判为应用功能失败。

### 7. 流式增量只更新当前回答气泡

收到每个 SSE `delta` 时不再调用完整聊天渲染或重新解析/替换回答气泡的 Markdown，而是按 `session_id` 定位当前流式回答行并更新同一个文本节点；生成期间以保留换行的纯文本展示，回答完成后再渲染 Markdown。来源事件单独更新来源区域。首次插入流式回答、会话切换及最终回答落入历史时仍执行完整渲染。增量更新仅在用户原本位于滚动底部附近时以即时方式跟随滚动，流式回答行不重复播放入场动画，避免动画每次被重新触发造成闪动或打断阅读。

## Risks / Trade-offs

- [并发额度不足] → 不承诺无限并行；展示每个会话自己的限流/超时错误，并保留已成功会话。
- [多 worker/多副本下的同会话并发] → 首版锁只覆盖单 Uvicorn 进程；部署扩容前切换到分布式会话锁并增加跨进程测试。
- [页面切换导致增量回答暂时不可见] → 将活动流状态按 session_id 保存，切回时恢复；不把活动文本只放在 DOM。
- [刷新页面丢失未完成流] → 只保证已完成消息持久化；刷新后从服务端重新加载历史，未完成回答显示为中断，不承诺断点续传。
- [删除/退出后的迟到 SSE] → AbortController 加请求代次和会话存在性校验，阻止迟到事件写入其他会话或账号。
- [后端数据库与 Redis 历史交错] → 增加并发回归测试，确认不同 session_id 独立；若发现同 session 竞争，再按设计增加会话级锁。

## Migration Plan

1. 先增加前端按会话管理和可控流测试，不改变后端协议。
2. 实现会话切换、独立提交按钮状态、来源和错误隔离。
3. 本地启动前端和后端，验证两个新会话可同时生成，以及失败/完成顺序交错场景。
4. 检查同一会话重复提交、删除会话、退出登录和刷新页面行为。
5. 验证同会话冲突返回明确错误且释放锁，不影响其他会话；确认首版锁与单 worker 部署约束一致。

回滚方式：恢复前端旧的单流状态实现即可；由于本设计不改变数据库 schema、API 路径和 SSE 契约，不需要数据迁移回滚。
