## Why
（为什么要改）

项目已经有健身训练和饮食功能，但图片中提到的两个公开数据集还没有接入为可查询、可追溯的数据目录，训练安排与饮食营养也尚未形成有依据的联动。接入后，系统可以结合用户自己的训练计划和目标，基于获准使用的食材、菜谱及营养数据回答训练饮食问题；用户不认识动作时，也可以查看该动作对应且已获准展示的视频。

## What Changes
（改哪些内容）

- 为训练动作数据提供“先预览、再导入”的流程，并保留上游记录 ID、数据来源、版本和字段是否缺失等信息。
- 不要求操作人员手动克隆完整仓库或下载媒体文件；由显式触发的导入流程从固定 commit 获取白名单中的结构化 JSON 文件。文件版本与 SHA-256 校验信息写入预览/导入清单；日常查询使用本项目已导入的数据，不在每次提问时调用上游仓库或外部 API。
- 单独接入食材和菜谱目录。营养数值作为结构化数据存储并进行精确查询和确定性计算；RAG 只用于检索文字说明。
- 让动作、食材和菜谱可搜索，并能显示其数据来源；动作条目可以关联对应的演示视频。
- 用户询问训练期间或训练后的饮食时，结合当前登录用户自己的目标和训练安排，从获准的食材/菜谱及营养数据中组织回答；营养数值、计量基准和计算结果均标注来源，资料不足时明确说明。
- 对使用权已核实且允许当前展示方式的视频，提供视频或来源链接，并显示来源/署名；使用权未知或不允许展示的视频不得向用户开放。
- 用户选择食材或菜谱后，可将份量基准和营养数值预填到现有饮食表单；用户检查并明确确认后，才保存为个人饮食记录。
- 代码、动作文字、营养数据及视频的使用权分别审查；许可或再分发权不明确的数据和媒体先隔离，不因仓库被称为“开源”就默认可以展示或托管其视频。
- 最终只保留两个知识域：健身知识库（动作文字及其获准展示的视频媒体）和饮食知识库（食材、营养数据及菜谱）；视频是健身知识库的关联媒体，不另建第三个知识库。
- 新数据完成试点和验收后，通过单独、可预览且需明确确认的切换操作，清理现有全部知识文档（包括团队/用户上传文档）及其检索副本；普通导入和重试不得触发清理。
- 清理旧知识文档不得删除账号、团队、角色/权限、聊天、训练计划或个人饮食记录，也不得删除或重建共享 Milvus 集合。
- 新数据导入支持重复执行和中断后续跑；正式切换前，旧知识文档继续保留，避免新目录尚未验收时项目失去可用知识内容。

## Capabilities
（涉及哪些功能）

### New Capabilities
（新增功能）
- `exercise-knowledge-catalog`（健身动作知识目录）：预览、校验、导入和搜索动作记录，关联获准展示的动作视频，并显示数据及媒体来源。
- `food-nutrition-catalog`（食物营养目录）：预览、按许可筛选、导入并搜索食材和菜谱；基于结构化数据计算营养值，并结合当前用户自己的训练目标/安排回答训练饮食问题。

### Modified Capabilities
（修改现有功能）
- `nutrition-tracking`（饮食记录）：允许使用目录数据预填饮食记录草稿，同时保留用户检查、明确确认和账号数据隔离要求。

## Impact
（影响范围）

- 影响现有知识导入链路，以及 PostgreSQL、MongoDB、Elasticsearch、Milvus、Neo4j 的目录、来源映射和检索流程；还需支持动作与视频媒体的可靠关联和合规展示。
- 增加一次显式的全量旧知识文档切换清理，范围包括团队/用户上传的知识文档及其内容、向量、搜索索引和文档图谱映射；该清理不能由导入器隐式执行。
- 影响现有训练/饮食问答及饮食录入流程；回答训练饮食问题时只读取当前用户自己的训练资料，不改变记录所有权，也不自动保存建议。
- 新增按数据来源区分的导入、预览工具和测试。本方案不要求把 GitHub 仓库部署成运行时服务；视频使用外部展示还是本地托管，以已核实的媒体授权范围为准。
- 导入时需要网络访问固定版本的上游文件地址；不下载整个仓库、不执行上游代码、不请求视频 URL。上游不可用或文件校验失败时，导入中止且不开始写入应用数据。
- 数据许可、媒体展示/托管权及视频与动作的匹配关系审查，是正式发布的前置条件。图片中的数据数量和字段结构只是初步信息，实施前需要对固定版本重新核对。
