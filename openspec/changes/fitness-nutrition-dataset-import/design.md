## 背景

改造动机见 `proposal.md`，用户可观察到的行为要求见 `specs/`。项目已经有多存储知识导入链路（PostgreSQL 关系型数据库中的文档元数据、MongoDB 文档数据库中的正文、Elasticsearch 关键词检索、Milvus 向量检索和可选 Neo4j 图数据库），也有账号独立的饮食记录和图片识别草稿。现有动作转换器的数据格式与新数据源不同，并且会把多个动作合并到一个文档中，因此需要新增专用转换器并保留来源信息。实施前必须基于固定的上游版本重新核对记录数、数据结构和许可。

## 目标与非目标

**目标：**
- 将动作、食材和菜谱的具体数据保存在可追溯来源的结构化记录中。
- 最终只开放两个知识域：健身知识库（动作说明及关联视频媒体）和饮食知识库（食材、营养数据及菜谱）；视频不是第三个知识库。
- 复用现有检索增强生成（RAG）链路检索动作和菜谱的文字说明，但不通过向量相似度计算营养数值。
- 把当前登录用户自己的训练目标/安排与获准的食材、菜谱和营养数据关联起来，为训练相关饮食问题提供有来源依据的回答。
- 在动作详情中展示已核实有权展示、且能准确关联到该动作的视频；视频不可用时仍提供动作文字资料。
- 提供互相隔离的预览和正式导入模式；使用稳定来源标识，支持按来源查看状态、重试和回滚。
- 保留个人饮食记录的账号隔离以及用户明确确认后才保存的行为。

**非目标：**
- 不把任一 GitHub 仓库部署为运行时服务；产品日常使用不依赖 GitHub 在线可用。
- 不提供医疗诊断或治疗性饮食方案；不在没有数据依据时编造个体化热量/营养目标，也不自动修改训练计划或保存饮食建议。
- 不把仓库代码许可误当作其内含数据、菜谱、图片或视频的许可；没有核实授权的视频不下载、嵌入、托管或展示。
- 不用 AI 补齐缺失的动作字段、推测缺失的营养值，或根据未经核实的文字计算菜谱总营养。
- 不删除或重建共享 Milvus 集合；旧知识内容的清理必须按明确的文档 ID 删除其内容和派生索引，不得触碰用户账号、团队、角色/权限、聊天、训练计划或个人饮食记录。

## 设计决策

### 1. 固定远程版本，按需获取结构化文件

操作人员不需要手动克隆完整仓库。导入工具读取经过审核的来源清单，其中为每个数据集固定仓库地址、完整 commit SHA、允许读取的 JSON 文件路径、来源类别和许可状态。工具只在显式运行预览/导入命令时，通过 HTTPS 获取这些固定版本的文件；不得解析 `main`/`latest` 等可变引用，不得执行上游代码，不得在应用启动或用户提问时访问 GitHub、chisha 服务或其他上游 API。

获取到的文件先进入临时工作目录供转换器使用，不拉取 Git 历史、无关文件或仓库媒体。每个文件记录仓库、commit、路径、获取时间、字节数和 SHA-256。dry-run 输出可审阅的来源锁定清单；正式导入必须使用该清单并再次校验摘要，确保实际写入的字节与已审阅预览一致。下载失败、commit/路径无效、文件超出配置上限或摘要不匹配时，停止本次导入且不得开始写入应用数据。可以保留已审阅的锁定清单用于重试，但不得把大文件或视频自动归档到项目仓库。

来源清单显式区分数据类别和许可。动作元数据的 MIT 状态只适用于经核实由该许可覆盖的代码/文字字段，不能延伸到视频。`free-exercise-db-api` 记录中的视频 URL 只作为待审查元数据计数和标记；导入工具不得请求、下载、代理或向用户返回这些 URL。chisha 的食材与菜谱按每条记录的 `source` 字段分类：USDA 来源、中国食物成分表来源、自建来源和外部菜谱分别保留来源与许可说明；缺失/不明确的来源进入隔离。中国食物成分表的 `license_note` 记录出版社版权及“商用需授权”的限制，在操作人员确认适用范围前不标记为用户可见的已批准数据。不能仅凭仓库代码许可批准仓库内的数据。

每个数据转换器按实际固定版本的结构生成统一记录，并先输出输入、有效、重复、无效、隔离数量及样例。文档中的数据量仅作预期核对，不作为硬编码成功条件。正式导入后，正常查询只访问本项目数据库/索引，因此上游短暂不可用不影响已导入内容。

**考虑过的替代方案：**
- 每次用户提问时实时调用上游 API：不采用，因为这会让产品运行依赖第三方可用性、速率限制和不断变化的数据，也无法可靠保证回答引用的是已审核的固定版本。
- 要求用户手动下载或克隆完整仓库：不作为默认流程，因为会额外占用本地空间并带入无关文件/媒体；仅在网络受限或用户明确要求离线导入时，才允许提供等价的本地固定快照输入。
- 每次导入都获取最新 `main`：不采用，因为无法复现或审计，也可能在未重新审查许可时引入新数据。

### 2. 结构化目录数据与知识文档分开存储

在 PostgreSQL 中增加有版本迁移的数据表，用于保存数据集导入记录与来源、动作、动作视频媒体、食材、菜谱和菜谱食材。动作视频作为单独媒体记录，通过稳定的上游动作 ID 或经核验的映射关联动作；记录媒体来源、许可依据、允许的展示方式和状态。使用 `(dataset, revision, upstream_record_id)` 或稳定的来源标识保证不重复，并用精确小数类型保存数量和营养数值。通过状态字段避免隔离记录被选择。具体字段以实施时核实过的上游数据结构为准；为方便审计，保留原始数据或经审核的必要字段。

每个动作、每份菜谱说明分别生成检索增强生成（RAG）知识文档，不把大量上游记录合并成一份泛化文档。保存“来源记录到知识文档”的对应关系，让引用和限定来源检索能够指向准确记录。食材营养数值通过目录接口读取，不在向量文本中重复存储为权威营养数据。

RAG 文档创建时保持草稿和非公开状态。MongoDB 正文、Milvus 向量、Elasticsearch 文档、Neo4j 图谱以及 PostgreSQL 来源映射均成功写入后，才将 PostgreSQL 文档和 Elasticsearch 文档设为已发布/公开。若任一内容存储或来源映射失败，文档保持草稿/非公开，使用稳定文档 ID 重试；若最终发布步骤失败，导入器尽力将已更新的发布标记恢复为非公开，并报告失败阶段。按现有权限规则，作者本人仍可查看自己的非公开文档；其他账号不可见。

**考虑过的替代方案：**把所有数据都作为文本放进 Milvus，再让模型检索或计算营养值。未采用，因为这样无法保证精确查询，数值结果也不稳定。

### 3. 许可审查分别控制数据启用、索引和媒体

分别记录仓库代码、动作文字、营养/菜谱数据、图片和每项视频媒体的使用许可。许可状态使用 `pending_review`（待审查）、`approved`（已批准）、`restricted`（受限制）等明确值，并保存审查依据及允许的用途。视频需额外记录获准的使用方式，例如仅展示来源链接、嵌入播放或下载后托管；只启用明确获准的方式。许可未知、来源不明或授权不包含当前展示方式的资料继续隔离。许可是否批准由操作人员确认，不由模型推断，也不根据仓库代码许可自动推定。展示外部视频时采用允许来源清单，避免把任意来源 URL 当作可嵌入内容。

**考虑过的替代方案：**根据仓库首页的代码许可，将全部记录和视频自动标记为已批准，或直接下载所有视频到本地。未采用，因为仓库内代码、数据和媒体可能适用不同权利；视频许可也可能只允许链接或嵌入，不允许复制和托管。

### 4. 精确查询和 RAG 检索分开处理

增加动作、食材和菜谱的目录查询接口/服务。营养值从 PostgreSQL 读取；只有原始单位可以可靠换算时，才提供每 100 克的统一值，并保留原始计量基准。菜谱总营养使用已批准的食材数据和明确数量，通过精确小数数值计算；缺少食材数据或单位不兼容时，结果标记为不完整，而不是估算。舍入规则必须写明并测试。

动作步骤和菜谱说明等文字通过现有 Elasticsearch（ES）/Milvus 检索。增加来源到文档的映射和过滤，使指定数据集的请求只能引用映射到该数据集的文档。结果元数据返回来源名称、记录 ID 和版本。不得改变其他文档现有的账号可见性规则。

**考虑过的替代方案：**只在提示词里要求模型使用指定数据集。未采用，因为检索阶段仍可能给模型传入无关文档；必须在组装模型上下文之前进行来源过滤。

### 5. 训练饮食回答结合本人训练上下文和营养证据

处理训练期间或训练后的饮食问题时，使用鉴权得到的当前用户 ID 读取其本人可用的健身档案和有效训练计划，再查询许可已批准的食材/菜谱目录。不得接受请求参数指定其他用户，也不得把其他账号的计划或记录作为回答上下文。回答应说明参考了哪些训练目标/安排，并为营养数值附上数据来源、计量基准及计算依据；营养合计由结构化数据确定性计算，RAG 只辅助查找文字说明。缺少训练计划或档案时，明确说明缺少的个性化依据，询问用户补充，或将可提供的内容明确标为一般建议。不得凭空推算个体化营养目标，建议本身也不得自动写入饮食记录。

**考虑过的替代方案：**只根据用户问题和通用食物知识生成饮食回答。未采用，因为这样无法满足训练目标与建议相互匹配、且回答可追溯的要求。

### 6. 选择目录数据只创建草稿，不直接生成个人记录

用户明确选择已批准的食材或菜谱后，界面可以预填现有饮食表单。界面需要展示来源、份量基准、数量和对应营养值。用户可以修改或取消；只有明确提交/确认后才创建归属当前账号的饮食记录。访问目录接口不代表可以访问其他用户的饮食记录。

### 7. 导入和回滚仅作用于对应来源

使用来源清单记录版本、内容哈希、数量和导入状态。正式写入必须显式启动；重试不得造成重复记录。多存储写入失败时，报告失败的存储及来源标识，并保证修复后可以安全重试。停用/回滚只停用指定数据集版本，只删除或替换映射到该版本的目录记录、媒体关联、RAG 文档和向量；其他文档、用户训练计划和饮食记录保持不变。严禁删除共享 Milvus 集合。

### 8. 通过受控切换清理旧知识文档

最终运行状态仅保留健身知识库和饮食知识库。所有新来源完成许可审查、试点导入和验收后，操作人员再启动单独的旧知识文档清理流程。该流程必须先提供 dry-run 报告，列出将删除的旧文档及各存储对应记录数量；未明确执行清理操作时不得删除。

清理范围包括当前已存在的全部知识文档（包括团队/用户上传文档）及其 PostgreSQL 文档元数据、MongoDB 正文、Elasticsearch 索引项、Milvus 向量和仅由这些文档产生的图谱映射。实现必须按稳定文档 ID 精确删除或解除关联，不能 drop/truncate 共享集合、索引或数据库。用户、团队、角色/权限、聊天历史、训练计划、训练记录、个人饮食记录和营养图片记录不属于清理范围。若系统存在独立审核审计记录，应保留必要审计事实，但不得让已删除文档重新出现在用户列表或检索结果中。

清理流程与正式导入分离；普通导入、重试、版本回滚均不得触发全量清理。清理前必须记录待删数量并要求操作人员二次确认；清理后需验证旧文档不再可见或可检索，新健身/饮食目录仍可用，且受保护的账号和个人业务数据未变化。

**考虑过的替代方案：**在新数据尚未验收时先清空旧库。未采用，因为这样会让项目在新来源、转换器或索引未通过验证时失去现有知识服务。

## 风险与取舍

- **[上游结构或记录数与图片不一致]** → 固定数据版本，检查 README 和实际数据结构，通过 dry-run 校验样本及完整数量；不把预期数量硬编码为成功标准。
- **[食材或菜谱许可不清楚，或不同记录许可不同]** → 隔离相关记录；获得并记录许可审查结论后，才允许启用或建立 RAG 索引。
- **[视频所在仓库开源但媒体授权不明确]** → 对视频逐项核实来源、署名要求和允许的展示/复制方式；只开放获准方式，未确认的视频不显示。
- **[动作与视频关联错误或外部视频失效]** → 使用稳定来源 ID 或人工核验的映射；视频播放失败时标记不可用并保留文字说明，不自动替换为未核实视频。
- **[营养单位无法确定换算方式]** → 保留原始计量基准；无法可靠换算时不提供统一值或计算结果。
- **[训练饮食回答缺少用户上下文或营养依据]** → 仅使用当前用户资料；缺少计划/档案时说明限制，不声称个性化；缺少营养数据时标记不完整，不估算。
- **[不同数据版本的记录内容发生变化]** → 保存版本、内容哈希和来源映射；将新版本作为受控版本导入，不覆盖其他来源数据。
- **[共享 RAG 索引让指定来源查询混入其他文档]** → 根据来源映射解析允许的文档 ID，在检索及组装提示词前过滤；一起测试模型上下文和页面引用。
- **[多存储导入只完成一部分]** → 记录每条记录和每个存储的进度，保证写入幂等；文档在所有正文/索引/图谱/来源映射完成前保持非公开，并测试失败重试和按来源停用。
- **[全量清理误删用户业务数据或共享集合]** → 清理作为独立操作，先 dry-run、按文档 ID 执行并二次确认；保护账号、团队/权限、聊天、训练和个人饮食数据，禁止删除或重建共享集合。
- **[旧库先删、新库未就绪]** → 先完成新目录试点与验收，再执行清理；导入器默认永不触发全量删除。
- **[用户误以为目录建议是经过验证的权威结论]** → 展示数据来源和份量基准，要求用户检查并确认；不静默保存，也不暗示具有医疗认证。

## 迁移与回滚计划

1. 固定并检查两个数据源的版本；分别核实动作文字、食材/菜谱和视频媒体的许可及允许用途，再运行只读预览。
2. 以新增迁移方式增加目录、来源映射及动作媒体信息；部署后即使目录为空，原有功能也必须保持不变。
3. 先导入少量已获批准的数据，检查来源数量、动作与视频匹配、视频展示方式、营养计算和逐条引用。
4. 验证训练饮食问答只读取当前用户自己的训练档案/计划，并能给出带来源及计量基准的回答；缺少上下文时能明确告知。
5. 导入并启用其余已批准记录；许可未确认的数据和媒体继续隔离。
6. 新健身知识库（含获准视频）和饮食知识库试点及端到端验收通过后，生成旧知识文档清理预览，核对包含团队/用户上传文档在内的待删清单和数量。
7. 操作人员明确确认后，单独清理旧知识文档及其各存储副本；保留账号、团队/权限、聊天、训练和个人饮食数据，不删除或重建共享 Milvus 集合。
8. 清理后复验最终只开放健身与饮食两个知识域；动作视频仍按媒体许可状态控制。
9. 回滚新数据版本时，只停用指定来源版本；全量旧知识文档清理是独立切换操作，不由普通版本回滚隐式执行。

## 导入前置门槛

数据尚未获准前，可以实现解析器、数据库迁移、预览报告和测试；但只有完成并记录以下各项后，才允许正式写入或向用户开放数据：

1. 为每个上游来源固定准确的 commit 或 release，并记录获取日期。
2. 检查实际文件，分别记录数据数量、结构、来源，以及代码、动作文字、营养/菜谱、图片和视频的许可条款、署名要求及允许的展示/复制方式。
3. 记录哪些数据类别/记录已批准、受限制或仍待确认。只有已批准的数据可以正式导入；其他数据必须隔离。
4. 核实营养单位、食材计量基准、菜谱食材数量和份量/成品量的含义。不能在不作假设的前提下换算的数据，必须标记为不可用或不完整。
5. 对每个视频确认其与动作的对应关系、来源署名和获准展示方式；无法确认的视频不得启用。
6. 正式写入前，必须由操作人员明确确认固定版本的数据来源清单。

这些门槛决定哪些数据和媒体可以导入、检索或展示，不改变系统的权限边界。即使只有部分记录获得批准，本次改造仍可交付；未批准的视频始终保持隔离。
